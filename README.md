# Cozmic — parent theme

The shared block theme (Full Site Editing) behind every Cozmic client website.
Per-client sites run as **child themes** that override `theme.json` and nothing
else, so one design system serves the whole fleet.

- **Requires:** WordPress 6.7+, PHP 8.2+
- **Text domain / prefix:** `cozmic` / `cozmic_`
- **Architecture + decisions:** `docs/wordpress-product-architecture.md` in the
  `cozmic-platform` repo. Read the decisions before changing structure — most of
  what looks arbitrary here is load-bearing.

## What belongs in this repo

**Presentation only.** The governing rule:

> Plugin = what exists and what it does. Theme = how it looks and where it goes.

| Here | Not here |
|---|---|
| `theme.json` design tokens | Post types and meta → **Cozmic Core** |
| Templates and template parts | Roles and capabilities → **Cozmic Core** |
| Patterns | Options framework → **Cozmic Core** |
| Block style variations | Dashboard REST endpoints → **Cozmic Connect** |
| CSS that `theme.json` cannot express | WooCommerce templates → **Cozmic Commerce** (deferred) |

A client who switches themes must keep their content. If something here would
break that, it is in the wrong repo.

## Layout

```
style.css        Theme header + the little CSS theme.json cannot express
theme.json       Design tokens: palette, typography, spacing, element styles
functions.php    Theme supports, pattern categories, block style variations
templates/       Block templates (index, page, single, 404 …)
parts/           Header and footer template parts
patterns/        The shared pattern library — PHP files, auto-registered
assets/fonts/    Self-hosted variable woff2 (see the README there — not committed yet)
```

## Conventions

**Patterns over custom blocks.** A custom block ties content to a plugin —
deactivate it and the client gets "this block contains unexpected content" across
their site. A pattern is core blocks, so placed content survives anything. Start
at zero custom blocks and make each one earn its way in.

**Lock the inside of components, never the page.** Clients must stay free to add,
remove, and reorder whole sections. What gets locked is the internals of a
composed section, so a button cannot be dragged out of a card. Default to
`"lock":{"move":true,"remove":true}` on inner blocks. Reach for
`templateLock: "contentOnly"` only on the fiddliest components — it also strips
colour, spacing, and typography controls. `patterns/cta-banner.php` is the
worked example.

**Child themes are `theme.json`-only.** Per-client palettes are generated by the
dashboard at provisioning, not hand-written. Note that `theme.json` preset
*arrays* (palette, font sizes, spacing) are **replaced** wholesale by a child,
not merged per-slug — safe precisely because they are machine-generated.

**Colour slugs are a contract.** The palette defines nine slugs — `base`,
`contrast`, `surface`, `primary`, `secondary`, `primary-ink`, `secondary-ink`,
`on-primary`, `on-secondary`. The dashboard fills all nine per client from
`brandStyle()`. Use the slugs in patterns; never hard-code a hex.

Use `primary` as a fill with `on-primary` text on top; use `primary-ink` for
brand-coloured text on a light background. That split is what keeps contrast
readable for any client brand colour without hand-tuning.

## Local setup

There is no local environment by decision (D7) — development happens on a
Cloudways staging app, validation on a dedicated canary site, and releases ship
as GitHub Release tags consumed by Plugin Update Checker.

To run it anywhere: drop the folder in `wp-content/themes/`, add the two font
files, and activate.

## Releasing

Commit and develop freely. Nothing reaches client sites until a **GitHub Release
is tagged** — that tag is the "tested and ready" gate, and it means the canary
site has run it first. Bump `Version:` in `style.css` and `COZMIC_THEME_VERSION`
in `functions.php` together.
